# Описание структуры репозитория `golang/go`

## 1. Папка `.github` — Шаблоны взаимодействия
Здесь находятся файлы, которые GitHub использует для стандартизации общения с сообществом.
*   **`ISSUE_TEMPLATE`**: Содержит шаблоны (Markdown и YAML-формы) для создания новых задач (`Issues`). Это помогает пользователям сразу указывать нужную информацию (версию ОС, шаги воспроизведения), что экономит время разработчикам.

## 2. Папка `api` — Контроль обратной совместимости
Это "страж" стабильности языка. Здесь хранятся текстовые файлы-эталоны со списками всех разрешенных публичных функций и типов.
*   **Как это работает**: Информация в эти файлы **не записывается автоматически**. Наоборот, тесты сравнивают текущий код с этими файлами. Если разработчик добавил новую функцию, он обязан **вручную** вписать её в `api/next.txt`, иначе тесты не пройдут.
*   **Тестирование**: 
    ```bash
    $ cd ~/go_src/src 
    $ GOROOT=$(pwd)/.. go test cmd/api
    ```
*   **Bootstrap**: Для сборки текущей версии Go (например, из ветки `master`) требуется уже установленный рабочий Go (обычно не старше двух предыдущих версий).
*   **Сборка**: Выполняется скриптом `./make.bash` (или `all.bash` для запуска с тестами). Сборка происходит очень быстро. Готовые бинарные файлы компилятора и инструментов попадают в папку `bin`.

## 3. Папка `doc` — Документация и спецификации
Здесь лежат исходники официальных руководств и статей.
*   **`asm.html`**: Руководство по **Go-ассемблеру**. Это дополнительный слой абстракции (на базе синтаксиса Plan 9), который позволяет писать низкоуровневый код, используя виртуальные регистры (`FP`, `SB`, `SP`). Это обеспечивает аппаратную совместимость Go на разных платформах (`linux`, `windows`, `arm` и др.).
*   **Создание кода**: Текстовый ассемблер обрабатывается скриптом `src/cmd/asm/internal/asm/asm.go` (парсинг в структуры `Prog`), а затем превращается в байты кодировщиками в папках `src/cmd/internal/obj/[архитектура]`.
*   **Линкование**: За процесс сборки финального бинарника отвечает пакет `cmd/link` (точка входа — `src/cmd/link/main.go`). Логика адаптации под разные ОС описана в `src/cmd/link/internal/ld`.

## 4. Конвейер превращения Go-кода в машинный код
Для обычного Go-файла процесс выглядит так:
1.  **Текст Go**: Исходный код.
2.  **Токены**: Лексер нарезает текст на значимые символы (ключевые слова, идентификаторы).
3.  **AST (Abstract Syntax Tree)**: Построение дерева разбора.
4.  **Типизация**: Проверка логики программы и совместимости типов.
5.  **SSA (Static Single Assignment)**: Промежуточное представление, на котором происходит главная **оптимизация** кода.
6.  **Машинный код**: Генерация байтов под процессор и запись в объектный архив (`.a`).

## 5. Папка `lib` — Статические данные
Здесь находятся вспомогательные файлы ресурсов.
*   Например, `lib/time/zoneinfo.zip` — база данных часовых поясов. Go возит её с собой, чтобы работа с временем была независимой от обновлений операционной системы.

## 6. Папка `misc` — Дополнительные инструменты
«Чердак» репозитория. Здесь лежат полезные для сообщества, но не критичные для самого языка вещи:
*   Поддержка WebAssembly (`wasm_exec.js`).
*   Скрипты для запуска Go на iOS и Android.
*   Утилиты для бенчмарков и специфические примеры использования CGO.

## 7. Папка `pkg` — Результаты компиляции
Здесь хранятся скомпилированные части стандартной библиотеки (`.a` файлы).
*   **Кэширование**: Часть кэшей находится в `pkg/linux_amd64` (предустановленные модули), но основная рабочая часть кэша при сборке ваших проектов сохраняется в домашней директории: `/home/user/.cache/go-build/`.

## Внуренне устройство Go

### Файл `src/runtime/proc.go`. Тут организуется сам принцип `GMP`. Изначально горутины помещаются в структуры. Есть глобальный объект имеющий в своем составе массивы горутин для каждого потока. В каждом массиве потока хранятся горутины для данного потока. Имеется бесконечный цикл потока в виде перехода между метками. В этом цикле постоянно просматривается не закочились ли у меня горутины. Если горутины отведенные для потока заканчиваются то они берутся из массивов горутин других потоков и выполняются.

### Файл `src/runtime/malloc.go`. Тут происходит выделение памяти для создаваемых объектов. Тут же происходит резервирование памяти от процессора. С выделением памяти очень много тонкосей и это приводит к экономию памяти, более быстрой работе с памятью, или же наоборот если не знать.

### Файл `src/runtime/mgc.go`. Тут реализовано освобождение памяти. Всё время работаю горутины которые помечают всё числами 1(серый, когда продолжает работать с этим объектом, черный - когда объект определяется как живой окончательно). При обходе объектов происходят внутренние блокировки чтобы объекты замерли на время и не менялись. Чистка объектов происходит не сразу а постепенно по мере выделения памяти для новых структур с помощью `malloc`. Для выясненения состояний структур создаётся битовая карта. Обход происходит параллельный. Если некоторые горутины которые обходят заканчивают обход своих структур, он берут структуры из других горутин. 

### Файл `src/runtime/runtime2.go`. Главные структуры тут `iface` и `eface`. `iface` хранит методы объекта в памяти, `data` - это ссылка на сам объект-экземпляр в памяти. `eface` хранит `_type` тип объекта который ему присвоили и сами данные `data`. К данным непосредственно в интерфейсе обращаться нельзя. Для этого нужно сделать type assertation `user := i.(*User)`.

### Файл `src/runtime/chan.go`. Тут имеется основная структура `hchan` которая представляет из себя структуру каналов в Go. В нём хранятся индексы для следущих чтений из канала, а также индексы куда будут записываться данные в канал. Сами данные хранятся в виде массива. Если место для записи есть, данная записывается. Если места нет, то происходит регистрация в `sudog`, блокировка и вызов `gopark`, которая отправляет содержущую их горутину в спящий режим. Каналы нельзя использовать для хранения данных и состояний. Каналы это средство для передачи.

### Паттерны при разборе модуля `net/http`: Это в основном паттерны потоковой обработки данных в бесконечных циклах, накопления данных во внутренних структурах с целью последущей передачи, вызов горутин при получении новых данных(конкурентность) 

### Паттерны при разборе `io` и `bufio`: Это паттерны работы с файлами с применением буферизации данных. К примеру, данные в файл не попадают, а попадают в буфер и только после вызова метода `Flash` данные сохраняются в файл. Либо это чтение из файла в бесконечном цикле до достижения конца файла.

### Паттерны `context`: Это о том чтобы отменять горутины по внешнему вызову или по истечению времени. Также это о том чтобы передавать данные в контекст. При передаче данных в контекст лучше создавать свой собственный тип переменных, а не писать непосредственно `string`, `int`, потому что так можно данные случайно поменять, а когда заводим свои собственные типы переменных, менять сложнее и это действует как защита данных от измненения.

### Можно вызывать C-код из Go. Вызов требует дополнительных расходов и занимает больше времени чем это же сделаем сам код Go. Если сравнить C-код и Go-код то разница минимальная.

### Если говорить про теневую память команды `go test -race`, то это о том что тестовая программа заглядывает в горутину и отмечает переменные горутине выделяя дополнительную память. Например, она отметила что есть переменная и отметила что туда можно что-то записать. И потом через некоторое время снова заглянула туда и отметила что отуда можно прочитать. При этом программа смотрит защищена ли эта переменная с помощью `atomic` или мьютекса и если не защищена выбрасывает ошибку.

### Приёмы минимизаций данных в куче с целью ускорения работы программ на Go
- Плохо маленькие структуры из функций передавать по ссылке, потому что происходит копирование структуры в кучу. Гораздо проще просто передать для копирования
- Если нужны временные объекты постоянно, то не нужно их постоянно создавать, потому что тратится очень много ресурсов на создание и уничтожение инстансов. Лучше использовать `sync.Pool` для работы с объектами
- Лучше выделять примерное количество памяти заранее, потому что каждое расширение - это трата ресурсов. Если есь возможность указывать `capacity`, то лучше указывать
- Любая передача переменных в `interface{}` приводит к бегству данных в кучу. Поэтому, лучше создавать функции со строго типизацией чем с помощью интерфейсов. Поэтому как аргумент `iterface{}` лучше не использовать
- Лучше избегать замыканий, потому чо каждое замыкание это передача данных в кучу. Лучше передавать переменные через аргументы
- Слишком большие слайсы в функции могут убегать в стек, поэтому лучше создавать маленькие стеки с фиксированным размером, либо массивы. Они более склонные оставаться в стеке
- Мапы это тяжелый объект в кучу. Чтобы GC не нагружать элементы в мапе лучше не делать по ссылке


Понимание Escape Analysis превращает тебя из простого кодера в инженера, который понимает «цену» каждой строчки. Вот в чем реальная польза:
Борьба с нагрузкой на GC: Если твой сервис начинает «тормозить» или жрать много CPU, причина часто в том, что мусорщик (Garbage Collector) не успевает вычищать кучу. Зная правила утечек, ты можешь переписать горячий участок кода так, чтобы данные оставались на стеке. Это дает колоссальный прирост производительности без смены железа.
Оптимизация интерфейсов: Ты начнешь видеть, где использование interface{} (например, в логгерах или fmt.Printf) создает лишнюю аллокацию. В высоконагруженных системах вместо интерфейсов часто используют типизированные методы, чтобы не гонять данные в кучу.
Правильный дизайн API: Ты перестанешь возвращать указатели (*T) там, где это не нужно. Передача по значению (T) часто быстрее, так как копия структуры на стеке дешевле, чем работа с объектом в куче через указатель.
Эффективные слайсы: Ты поймешь, почему выгодно заранее задавать cap (емкость) слайса через make([]int, 0, 100). Это помогает компилятору и рантайму избежать лишних переаллокаций в куче при расширении массива.
Чтение чужого кода: Ты начнешь понимать, почему в стандартной библиотеке Go или в крутых фреймворках (типа fasthttp) код написан именно так — иногда он выглядит странно (например, переиспользование объектов), но это сделано ради борьбы с аллокациями.
