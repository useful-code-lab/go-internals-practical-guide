# Описание структуры репозитория `golang/go`

## 1. Папка `.github` — Шаблоны взаимодействия
Здесь находятся файлы, которые GitHub использует для стандартизации общения с сообществом.
*   **`ISSUE_TEMPLATE`**: Содержит шаблоны (Markdown и YAML-формы) для создания новых задач (`Issues`). Это помогает пользователям сразу указывать нужную информацию (версию ОС, шаги воспроизведения), что экономит время разработчикам.

## 2. Папка `api` — Контроль обратной совместимости
Это "страж" стабильности языка. Здесь хранятся текстовые файлы-эталоны со списками всех разрешенных публичных функций и типов.
*   **Как это работает**: Информация в эти файлы **не записывается автоматически**. Наоборот, тесты сравнивают текущий код с этими файлами. Если разработчик добавил новую функцию, он обязан **вручную** вписать её в `api/next.txt`, иначе тесты не пройдут.
*   **Тестирование**: 
    ```bash
    $ cd ~/go_src/src 
    $ GOROOT=$(pwd)/.. go test cmd/api
    ```
*   **Bootstrap**: Для сборки текущей версии Go (например, из ветки `master`) требуется уже установленный рабочий Go (обычно не старше двух предыдущих версий).
*   **Сборка**: Выполняется скриптом `./make.bash` (или `all.bash` для запуска с тестами). Сборка происходит очень быстро. Готовые бинарные файлы компилятора и инструментов попадают в папку `bin`.

## 3. Папка `doc` — Документация и спецификации
Здесь лежат исходники официальных руководств и статей.
*   **`asm.html`**: Руководство по **Go-ассемблеру**. Это дополнительный слой абстракции (на базе синтаксиса Plan 9), который позволяет писать низкоуровневый код, используя виртуальные регистры (`FP`, `SB`, `SP`). Это обеспечивает аппаратную совместимость Go на разных платформах (`linux`, `windows`, `arm` и др.).
*   **Создание кода**: Текстовый ассемблер обрабатывается скриптом `src/cmd/asm/internal/asm/asm.go` (парсинг в структуры `Prog`), а затем превращается в байты кодировщиками в папках `src/cmd/internal/obj/[архитектура]`.
*   **Линкование**: За процесс сборки финального бинарника отвечает пакет `cmd/link` (точка входа — `src/cmd/link/main.go`). Логика адаптации под разные ОС описана в `src/cmd/link/internal/ld`.

## 4. Конвейер превращения Go-кода в машинный код
Для обычного Go-файла процесс выглядит так:
1.  **Текст Go**: Исходный код.
2.  **Токены**: Лексер нарезает текст на значимые символы (ключевые слова, идентификаторы).
3.  **AST (Abstract Syntax Tree)**: Построение дерева разбора.
4.  **Типизация**: Проверка логики программы и совместимости типов.
5.  **SSA (Static Single Assignment)**: Промежуточное представление, на котором происходит главная **оптимизация** кода.
6.  **Машинный код**: Генерация байтов под процессор и запись в объектный архив (`.a`).

## 5. Папка `lib` — Статические данные
Здесь находятся вспомогательные файлы ресурсов.
*   Например, `lib/time/zoneinfo.zip` — база данных часовых поясов. Go возит её с собой, чтобы работа с временем была независимой от обновлений операционной системы.

## 6. Папка `misc` — Дополнительные инструменты
«Чердак» репозитория. Здесь лежат полезные для сообщества, но не критичные для самого языка вещи:
*   Поддержка WebAssembly (`wasm_exec.js`).
*   Скрипты для запуска Go на iOS и Android.
*   Утилиты для бенчмарков и специфические примеры использования CGO.

## 7. Папка `pkg` — Результаты компиляции
Здесь хранятся скомпилированные части стандартной библиотеки (`.a` файлы).
*   **Кэширование**: Часть кэшей находится в `pkg/linux_amd64` (предустановленные модули), но основная рабочая часть кэша при сборке ваших проектов сохраняется в домашней директории: `/home/user/.cache/go-build/`.

# Внутреннее устройство Go Runtime (Core Components)

Краткий обзор архитектуры и ключевых файлов исходного кода языка Go (`src/runtime`).

---

## 1. Планировщик и модель GMP (`src/runtime/proc.go`)
В этом файле реализована логика многопоточности и распределения задач.

*   **Сущности:** 
    *   **G** (Goroutine) — легковесный поток.
    *   **M** (Machine) — поток ОС.
    *   **P** (Processor) — ресурс для выполнения Go-кода (локальный планировщик).
*   **Work Stealing:** Если у потока (`P`) заканчиваются горутины в локальной очереди, он переходит в режим "кражи": берет задачи из глобальной очереди или ворует половину задач у других процессоров.
*   **Цикл выполнения:** В файле реализован бесконечный цикл планировщика (`schedule`), который переключает контексты горутин, обеспечивая непрерывную работу программы.

## 2. Аллокатор памяти (`src/runtime/malloc.go`)
Здесь сосредоточена логика выделения памяти и взаимодействия с ОС.

*   **TCMalloc:** Go использует концепцию Thread-Caching Malloc. Память нарезается на "спаны" (spans) фиксированных размеров.
*   **Оптимизация:** Маленькие объекты аллоцируются в локальный кэш процессора (`mcache`) без блокировок, что критически ускоряет работу.
*   **Резервирование:** В файле описано, как рантайм запрашивает у операционной системы большие куски памяти (arenas) для последующей нарезки.

## 3. Сборщик мусора (GC) (`src/runtime/mgc.go`)
Реализация **Concurrent Mark-and-Sweep** (параллельная пометка и очистка).

*   **Трехцветный алгоритм:** 
    *   **Белый:** Объект — кандидат на удаление.
    *   **Серый:** Объект найден, но его связи еще не проверены.
    *   **Черный:** Объект гарантированно "живой".
*   **Параллелизм:** Обход объектов идет параллельно с работой программы. Если одна горутина-маркер заканчивает свою ветку, она помогает другим (Mark Assisting).
*   **Write Barrier:** Механизм, предотвращающий удаление объекта, если во время работы GC программа изменила указатель на него.
*   **Очистка:** Удаление мусора происходит не мгновенно, а постепенно (пропорционально новым аллокациям в `malloc`), чтобы не создавать длинных пауз.

## 4. Интерфейсы и типы (`src/runtime/runtime2.go`)
В этом файле описаны "скелеты" основных структур данных Go.

*   **eface (Empty Interface):** Структура для `interface{}`. Содержит тип (`_type`) и указатель на данные (`data`).
*   **iface (Interface with methods):** Структура для интерфейсов с набором методов. Содержит:
    *   `itab`: Таблица методов и информация о типе.
    *   `data`: Ссылка на сам экземпляр объекта.
*   **Type Assertion:** Поскольку прямой доступ к данным в интерфейсе запрещен, используется механизм приведения типа: 
    ```go
    user := i.(*User) // Проверка соответствия типов на уровне runtime
    ```


## 5. Планировщик и модель GMP (`src/runtime/proc.go`)
Здесь реализована логика многопоточности и распределения задач между ядрами процессора.

*   **Сущности:** 
    *   **G** (Goroutine) — легковесный поток.
    *   **M** (Machine) — поток ОС.
    *   **P** (Processor) — локальный планировщик.
*   **Work Stealing:** Если у процессора (`P`) заканчиваются горутины, он забирает задачи из глобальной очереди или «ворует» половину задач у других `P`.
*   **Цикл выполнения:** В файле реализован бесконечный цикл планировщика, который переключает контексты горутин, обеспечивая непрерывную работу.

## 6. Аллокатор памяти (`src/runtime/malloc.go`)
Логика выделения памяти и взаимодействия с операционной системой.

*   **TCMalloc:** Использование локальных кэшей (`mcache`) для каждого `P`, что позволяет выделять память под мелкие объекты без блокировок.
*   **Эффективность:** Память нарезается на "спаны" (spans). Резервирование у ОС происходит большими аренами, что экономит ресурсы на системных вызовах.

## 7. Сборщик мусора (GC) (`src/runtime/mgc.go`)
Реализация параллельного трехцветного алгоритма (Concurrent Mark-and-Sweep).

*   **Алгоритм:** Объекты помечаются как белые (кандидаты на удаление), серые (в процессе проверки) или черные (живые).
*   **Параллелизм:** Сборщик работает одновременно с основной программой. Для синхронизации используется **Битовая карта** и **Write Barrier** (барьер записи).
*   **Инкрементальная очистка:** Память освобождается постепенно по мере новых аллокаций в `malloc`, что минимизирует паузы (Stop The World).

## 8. Интерфейсы и структуры (`src/runtime/runtime2.go`)
Описание базовых типов данных рантайма.

*   **eface:** Пустой интерфейс (`interface{}`). Хранит тип (`_type`) и данные (`data`).
*   **iface:** Интерфейс с методами. Содержит таблицу методов (`itab`) и ссылку на объект.
*   **Безопасность:** Прямой доступ к данным запрещен. Для работы требуется **Type Assertion**: `user := i.(*User)`.

## 9. Устройство каналов (`src/runtime/chan.go`)
Каналы — это средство передачи данных (коммуникации), а не хранения состояний.

*   **Структура `hchan`:** Содержит кольцевой буфер (массив) и индексы чтения/записи.
*   **Блокировка:** Если канал полон или пуст, горутина регистрируется в структуре `sudog`, вызывается `gopark` и поток переходит в режим ожидания до появления данных или места.

## 10. Паттерны стандартной библиотеки

### Сетевое взаимодействие (`net/http`)
*   **Конкурентность:** Использование бесконечных циклов для приема соединений и вызов новой горутины на каждый запрос. Накопление данных во внутренних структурах перед передачей.

### Буферизация (`io` и `bufio`)
*   **Отложенная запись:** Данные пишутся в промежуточный буфер и попадают в файл только после его заполнения или вызова `Flush()`. 
*   **Потоковое чтение:** Чтение в цикле до достижения конца файла (`EOF`).

### Контекст (`context`)
*   **Отмена задач:** Использование для прерывания горутин по таймауту или сигналу.
*   **Типизация данных:** При передаче значений через контекст рекомендуется создавать **собственные типы ключей**. Это защищает данные от случайной перезаписи другими пакетами.

## 12. Взаимодействие с C (CGO)
*   **Производительность:** Вызов C-кода из Go возможен, но требует дополнительных накладных расходов (переключение стеков). Разница в скорости выполнения логики между Go и C часто минимальна.

## 13. Детектор гонок (`go test -race`)
*   **Теневая память:** Тестовая программа выделяет доп. память для отслеживания обращений к переменным.
*   **Анализ:** Проверяет, защищена ли переменная мьютексом или `atomic`. Если обнаруживается конкурентный доступ на запись и чтение без защиты — фиксируется Race Condition.

## 14. Контрибьютинг в Go
Для участия в развитии экосистемы Go можно использовать следующие ресурсы:

*   **Агрегаторы задач:** [Good First Issue (Go)](https://github.com) — задачи для новичков.
*   **Поиск на GitHub:** Запросы вида `help:wanted language:go` или `label:"help wanted"`.
*   **Сферы:** Инфраструктура (Docker, K8s), облака, базы данных и системные библиотеки.



## 10. Минимизация аллокаций в куче (Heap)

Оптимизация распределения памяти позволяет значительно ускорить работу программы, снижая нагрузку на Garbage Collector (GC).

*   **Передача по значению vs По ссылке:** 
    Для маленьких структур выгоднее передавать их в функции **по значению** (копированием). Передача по ссылке (`*Struct`) часто заставляет объект "убегать" в кучу (Escape Analysis), что дороже, чем простое копирование в стеке.
    
*   **Использование `sync.Pool`:** 
    Если программа постоянно создает и уничтожает временные объекты (например, буферы), используйте `sync.Pool`. Это позволяет **переиспользовать** инстансы объектов, экономя ресурсы на их выделении и последующей очистке сборщиком мусора.

*   **Предварительное выделение памяти (Pre-allocation):** 
    Каждое расширение слайса (`append`) или мапы при нехватке места — это аллокация новой памяти и копирование старых данных. Всегда указывайте **capacity** (`make([]T, 0, cap)`), если примерный объем данных известен заранее.

*   **Избегайте `interface{}` в аргументах:** 
    Любая передача переменной в пустой интерфейс (`eface`) практически всегда приводит к её **бегству в кучу**. Старайтесь использовать строгую типизацию вместо универсальных интерфейсов там, где это критично для производительности.

*   **Осторожность с замыканиями (Closures):** 
    Замыкания часто захватывают переменные из внешнего контекста, перенося их в кучу. Чтобы сохранить данные в стеке, лучше передавать их явно через **аргументы функции**.

*   **Размер слайсов и массивы:** 
    Слишком большие слайсы могут быть вынесены в кучу планировщиком. Для небольших фиксированных наборов данных лучше использовать **массивы** (например, `[64]byte`) — они с гораздо большей вероятностью останутся в быстром стеке.

*   **Оптимизация Map:** 
    Мапа — это тяжелый объект. Чтобы облегчить работу GC, старайтесь не хранить в мапе **значения по ссылке** (указатели). Чем меньше указателей внутри мапы, тем быстрее сборщик мусора сможет её просканировать.
