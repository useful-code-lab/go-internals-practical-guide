# Описание структуры репозитория `golang/go`

## 1. Папка `.github` — Шаблоны взаимодействия
Здесь находятся файлы, которые GitHub использует для стандартизации общения с сообществом.
*   **`ISSUE_TEMPLATE`**: Содержит шаблоны (Markdown и YAML-формы) для создания новых задач (`Issues`). Это помогает пользователям сразу указывать нужную информацию (версию ОС, шаги воспроизведения), что экономит время разработчикам.

## 2. Папка `api` — Контроль обратной совместимости
Это "страж" стабильности языка. Здесь хранятся текстовые файлы-эталоны со списками всех разрешенных публичных функций и типов.
*   **Как это работает**: Информация в эти файлы **не записывается автоматически**. Наоборот, тесты сравнивают текущий код с этими файлами. Если разработчик добавил новую функцию, он обязан **вручную** вписать её в `api/next.txt`, иначе тесты не пройдут.
*   **Тестирование**: 
    ```bash
    $ cd ~/go_src/src 
    $ GOROOT=$(pwd)/.. go test cmd/api
    ```
*   **Bootstrap**: Для сборки текущей версии Go (например, из ветки `master`) требуется уже установленный рабочий Go (обычно не старше двух предыдущих версий).
*   **Сборка**: Выполняется скриптом `./make.bash` (или `all.bash` для запуска с тестами). Сборка происходит очень быстро. Готовые бинарные файлы компилятора и инструментов попадают в папку `bin`.

## 3. Папка `doc` — Документация и спецификации
Здесь лежат исходники официальных руководств и статей.
*   **`asm.html`**: Руководство по **Go-ассемблеру**. Это дополнительный слой абстракции (на базе синтаксиса Plan 9), который позволяет писать низкоуровневый код, используя виртуальные регистры (`FP`, `SB`, `SP`). Это обеспечивает аппаратную совместимость Go на разных платформах (`linux`, `windows`, `arm` и др.).
*   **Создание кода**: Текстовый ассемблер обрабатывается скриптом `src/cmd/asm/internal/asm/asm.go` (парсинг в структуры `Prog`), а затем превращается в байты кодировщиками в папках `src/cmd/internal/obj/[архитектура]`.
*   **Линкование**: За процесс сборки финального бинарника отвечает пакет `cmd/link` (точка входа — `src/cmd/link/main.go`). Логика адаптации под разные ОС описана в `src/cmd/link/internal/ld`.

## 4. Конвейер превращения Go-кода в машинный код
Для обычного Go-файла процесс выглядит так:
1.  **Текст Go**: Исходный код.
2.  **Токены**: Лексер нарезает текст на значимые символы (ключевые слова, идентификаторы).
3.  **AST (Abstract Syntax Tree)**: Построение дерева разбора.
4.  **Типизация**: Проверка логики программы и совместимости типов.
5.  **SSA (Static Single Assignment)**: Промежуточное представление, на котором происходит главная **оптимизация** кода.
6.  **Машинный код**: Генерация байтов под процессор и запись в объектный архив (`.a`).

## 5. Папка `lib` — Статические данные
Здесь находятся вспомогательные файлы ресурсов.
*   Например, `lib/time/zoneinfo.zip` — база данных часовых поясов. Go возит её с собой, чтобы работа с временем была независимой от обновлений операционной системы.

## 6. Папка `misc` — Дополнительные инструменты
«Чердак» репозитория. Здесь лежат полезные для сообщества, но не критичные для самого языка вещи:
*   Поддержка WebAssembly (`wasm_exec.js`).
*   Скрипты для запуска Go на iOS и Android.
*   Утилиты для бенчмарков и специфические примеры использования CGO.

## 7. Папка `pkg` — Результаты компиляции
Здесь хранятся скомпилированные части стандартной библиотеки (`.a` файлы).
*   **Кэширование**: Часть кэшей находится в `pkg/linux_amd64` (предустановленные модули), но основная рабочая часть кэша при сборке ваших проектов сохраняется в домашней директории: `/home/user/.cache/go-build/`.

## Внуренне устройство Go

### Файл `src/runtime/proc.go`. Тут организуется сам принцип `GMP`. Изначально горутины помещаются в структуры. Есть глобальный объект имеющий в своем составе массивы горутин для каждого потока. В каждом массиве потока хранятся горутины для данного потока. Имеется бесконечный цикл потока в виде перехода между метками. В этом цикле постоянно просматривается не закочились ли у меня горутины. Если горутины отведенные для потока заканчиваются то они берутся из массивов горутин других потоков и выполняются.

### Файл `src/runtime/malloc.go`. Тут происходит выделение памяти для создаваемых объектов. Тут же происходит резервирование памяти от процессора. С выделением памяти очень много тонкосей и это приводит к экономию памяти, более быстрой работе с памятью, или же наоборот если не знать.


Чтобы вырасти из прикладного разработчика в системного инженера, нужно двигаться от синтаксиса языка к "железу" и рантайму. Вот логичный маршрут:

## 1. Runtime — Сердце языка
Рантайм — это код, который живет внутри вашего бинарника и управляет программой.
*   **Планировщик (Scheduler):** Изучите модель **G-M-P** (Goroutine, Machine, Processor). 
    *   *Файл:* `src/runtime/proc.go`. Поймите, как тысячи горутин распределяются по реальным ядрам процессора.
*   **Управление памятью (Memory Management):** Разберитесь, как работает аллокатор (mspan, mcache).
    *   *Файл:* `src/runtime/malloc.go`.
*   **Сборщик мусора (GC):** Узнайте, что такое **Concurrent Mark & Sweep** и почему паузы (STW) в Go такие короткие.
    *   *Файл:* `src/runtime/mgc.go`.

## 2. Анатомия типов и интерфейсов
Поймите, как Go "видит" данные во время работы.
*   **Интерфейсы:** Изучите структуры `iface` и `eface`. Это два указателя: на данные и на таблицу методов. 
    *   *Файл:* `src/runtime/runtime2.go`. Это объяснит, почему интерфейс с `nil`-объектом внутри сам не является `nil`.
*   **Каналы (Channels):** Посмотрите, как устроена структура `hchan` и как работает очередь и блокировка горутин при передаче данных.
    *   *Файл:* `src/runtime/chan.go`.

## 3. Стандартная библиотека как эталон
Библиотеки в `src/` — это лучший учебник по написанию идиоматичного кода.
*   **`net/http`**: Как реализован сервер. Лучший пример конкурентности и работы с сокетами.
*   **`io` и `bufio`**: Магия интерфейсов `Reader` и `Writer` — база композиции в Go.
*   **`context`**: Как устроено дерево отмены задач и передача сигналов между горутинами.

## 4. Системное взаимодействие (CGO и ABI)
Поймите, как Go общается с внешним миром и ОС.
*   **CGO**: Попробуйте вызвать C-функцию. Узнайте цену перехода: переключение стеков и стоимость вызова.
*   **Race Detector**: Разберитесь, как `go test -race` находит ошибки через теневую память (Shadow Memory).

## 5. Практика: Контрибьютинг
Ничто не учит лучше, чем попытка исправить баг в самом языке.
*   Найдите задачу с меткой `good first issue` в [репозитории Go на GitHub](https://github.com).
*   Пройдите путь от создания Issue до отправки патча через **Gerrit**. Ревью от инженеров Google — это лучший "бесплатный университет".

## 6. Теория компиляции
Раз вы уже затронули SSA и AST:
*   Углубитесь в то, как работают оптимизаторы. Прочтите про **Escape Analysis** (анализ утечки памяти в кучу). 
*   Команда для анализа: `go build -gcflags="-m"` — покажет, почему переменная ушла в кучу, а не осталась на стеке.
