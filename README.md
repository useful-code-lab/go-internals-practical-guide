# Go Internals: как Go работает внутри

Практический разбор внутреннего устройства **Go** — от исходного кода компилятора и runtime до работы goroutine, каналов, интерфейсов, Garbage Collector и управления памятью.

Этот репозиторий создан для разработчиков, которые хотят понимать не только **как писать код на Go**, но и **что происходит с ним после запуска**.

---

## Зачем нужен этот репозиторий?

Большую часть времени Go позволяет не думать о внутренних механизмах языка.

Можно написать:

```go
go worker()
```

и получить конкурентное выполнение.

Можно создать:

```go
data := make([]byte, 1024)
```

и не заниматься ручным управлением памятью.

Можно передать значение через:

```go
ch <- data
```

и не думать о том, как одна goroutine будет ждать другую.

Но когда появляется проблема с **производительностью, памятью, конкурентностью или неожиданным поведением программы**, понимания поверхностного уровня уже может быть недостаточно.

Именно здесь полезно знание внутренних механизмов Go.

Этот проект помогает связать привычный Go-код с тем, что происходит внутри runtime и компилятора.

---

## Что можно получить из проекта?

Изучая материалы репозитория, можно лучше понимать:

* почему goroutine дешевле потоков ОС;
* как Go распределяет goroutine между потоками;
* что такое модель **G-M-P**;
* как работает scheduler;
* как реализован **work stealing**;
* почему некоторые объекты попадают в heap;
* как работает **escape analysis**;
* почему определённый код создаёт лишние аллокации;
* как Garbage Collector находит и освобождает объекты;
* зачем нужен write barrier;
* как устроены interfaces внутри runtime;
* как работают channels;
* почему операции с каналами могут блокировать goroutine;
* как `net/http` использует конкурентность;
* зачем нужны `io` и `bufio`;
* как работает `context`;
* какие последствия имеет использование CGO;
* как работает `go test -race`;
* где искать причины проблем с памятью и конкурентностью;
* какие оптимизации действительно могут уменьшить количество аллокаций.

Главная цель — не запомнить устройство каждого файла runtime, а научиться **объяснять поведение собственного Go-кода через механизмы, которые находятся под ним**.

# Как читать этот репозиторий

Материалы построены вокруг нескольких уровней.

```text
Ваш Go-код
    ↓
Компилятор
    ↓
AST / типизация / SSA
    ↓
Машинный код
    ↓
Runtime
    ├── Scheduler
    ├── Goroutines
    ├── Memory Allocator
    ├── Garbage Collector
    ├── Channels
    └── Interfaces
    ↓
Операционная система
    ↓
CPU / Memory
```

Такой подход позволяет рассматривать Go не как набор отдельных конструкций языка, а как целостную систему.

Основная часть исходников находится в `src`.

* компилятора;

# 2. Как Go-код превращается в машинный код

Упрощённо процесс можно представить так:

```text
Go source code
      ↓
Lexing
      ↓
Parsing
      ↓
AST
      ↓
Type checking
      ↓
SSA
      ↓
Optimization
      ↓
Machine code
      ↓
Linking
      ↓
Executable
```

Особое внимание уделено **SSA (Static Single Assignment)**.

Это один из важных этапов компиляции, на котором компилятор преобразует и оптимизирует программу перед генерацией машинного кода.

Понимание этого процесса помогает разобраться, почему компилятор Go может:

* устранять ненужные операции;
* оптимизировать код;
* выполнять inline;
* анализировать escape;
* преобразовывать программу перед генерацией машинных инструкций.

# 3. Scheduler и модель GMP

Одна из ключевых частей runtime находится в:

```text
src/runtime/proc.go
```

Здесь реализована значительная часть механизма планирования выполнения goroutine.

Основные сущности:

```text
G — Goroutine
M — Machine / поток ОС
P — Processor
```

Упрощённо:

```text
        P
       /|\
      / | \
     G  G  G
       |
       M
       |
    OS thread
```

Scheduler решает, какая goroutine должна выполняться и на каком системном потоке.

Также реализованы механизмы, позволяющие перераспределять работу между процессорами.

Например, когда локальная очередь одного `P` становится пустой, scheduler может попытаться получить работу из других источников.

### Практическая польза

Понимание scheduler помогает объяснить:

* почему большое количество goroutine обычно не означает такое же количество потоков ОС;
* почему goroutine могут переключаться;
* откуда появляется конкуренция за CPU;
* почему блокирующая операция может влиять на выполнение;
* как Go использует несколько ядер процессора.

---

# 4. Управление памятью

Одна из самых полезных частей для разработчика находится вокруг:

```text
src/runtime/malloc.go
```

Runtime отвечает за выделение памяти для объектов Go и взаимодействие с операционной системой.

Важные понятия:

* `mcache`;
* `mspan`;
* arenas;
* heap;
* stack;
* allocation;
* garbage collection.

Особенно важно понимать разницу между:

```text
Stack
```

и

```text
Heap
```

Потому что расположение объекта в памяти напрямую связано с затратами на его жизненный цикл и работой GC.

---

# 5. Escape Analysis

Одна из наиболее практичных тем проекта — **escape analysis**.

Компилятор анализирует, может ли значение безопасно оставаться на стеке или его необходимо разместить в куче.

Например:

```go
func createUser() *User {
    user := User{}
    return &user
}
```

Здесь объект может потребовать размещения в heap, потому что его адрес используется после завершения функции.

Проверить информацию компилятора можно, например, так:

```bash
go build -gcflags="-m"
```

### Зачем это знать?

Это позволяет понимать причины некоторых аллокаций и осознаннее работать с:

* указателями;
* интерфейсами;
* замыканиями;
* возвращаемыми значениями;
* структурами;
* временными объектами.

Важно: не каждое использование указателя автоматически означает heap allocation. Решение принимает компилятор на основе анализа программы.

# 6. Garbage Collector

Основная логика GC находится в runtime.

Например:

```text
src/runtime/mgc.go
```

Go использует конкурентный сборщик мусора, который старается выполнять значительную часть работы параллельно с приложением.

Для понимания GC полезно знать концепцию трёх цветов:

```text
White
  ↓
Gray
  ↓
Black
```

А также:

* mark phase;
* sweep;
* write barrier;
* mark assist;
* mutator;
* heap scanning.

### Практическая польза

Понимание GC помогает объяснить:

* почему большое количество временных объектов может создавать дополнительную нагрузку;
* почему количество указателей имеет значение для сканирования heap;
* почему уменьшение ненужных аллокаций иногда улучшает производительность;
* как связаны allocation rate и работа GC.

---

# 7. Interfaces внутри Go

Внутреннее представление интерфейсов рассматривается через runtime-структуры.

В частности:

```text
eface
iface
itab
_type
data
```

На уровне языка достаточно написать:

```go
var value any
```

Но внутри runtime интерфейс должен хранить информацию о типе и данных.

Понимание этой модели помогает лучше разобраться в:

* type assertion;
* type switch;
* dynamic type;
* interface boxing;
* стоимости некоторых операций с интерфейсами.

# 8. Channels

Исходник механизма каналов находится в:

```text
src/runtime/chan.go
```

Внутри канала используется структура:

```text
hchan
```

Она отвечает за состояние канала, буфер и взаимодействие ожидающих goroutine.

Упрощённая схема:

```text
Producer
   │
   ▼
┌───────────────┐
│    Channel    │
│ ┌───┬───┬───┐ │
│ │ A │ B │ C │ │
│ └───┴───┴───┘ │
└───────────────┘
   │
   ▼
Consumer
```

Если операция невозможна немедленно, goroutine может перейти в состояние ожидания.

Это позволяет понять, что channel — не просто «очередь значений», а часть механизма синхронизации goroutine.

# 9. `net/http`

Стандартная библиотека Go активно использует возможности concurrency.

Изучение `net/http` помогает увидеть, как механизмы runtime используются уже на уровне реального сетевого сервера.

Можно проследить:

```text
TCP connection
      ↓
HTTP server
      ↓
request
      ↓
handler
      ↓
goroutine
```

Это хороший пример того, как низкоуровневые возможности runtime превращаются в удобный API.

---

# 10. `io` и `bufio`

Работа с I/O — ещё один пример того, где понимание внутренних механизмов помогает писать эффективный код.

Буферизация позволяет уменьшить количество операций с underlying writer/reader.

Упрощённо:

```text
Application
     ↓
   bufio
     ↓
 underlying reader/writer
     ↓
       OS
```

Изучение этих пакетов помогает понять, зачем существует буферизация и когда она может уменьшить количество операций ввода-вывода.

---

# 11. `context`

`context.Context` используется для управления жизненным циклом операций.

Например:

```text
Request
   │
   ├── Database query
   ├── HTTP request
   └── Goroutine
         │
         ▼
      Cancel
```

Если исходная операция отменена или истёк timeout, зависимые операции могут получить сигнал завершения.

Также рассматриваются рекомендации по передаче значений через context и использованию собственных типов ключей.

---

# 12. CGO

Go позволяет взаимодействовать с кодом на C через CGO.

Однако переход между Go и C имеет дополнительные механизмы runtime и накладные расходы.

Изучение CGO помогает понимать:

* когда действительно нужен C;
* какие дополнительные расходы возникают;
* почему использование CGO нельзя рассматривать как полностью бесплатный вызов обычной Go-функции.

# 13. Race Detector

Инструмент:

```bash
go test -race
```

помогает находить некоторые ошибки конкурентного доступа к памяти.

Он отслеживает обращения к памяти и анализирует потенциальные data race.

Это особенно полезно для программ с:

* goroutine;
* shared state;
* mutex;
* atomic operations;
* channels.

# 14. Минимизация аллокаций

Практическая часть проекта посвящена тому, как уменьшать ненужную работу с heap.

Рассматриваются:

### Pre-allocation

Если размер известен заранее:

```go
items := make([]Item, 0, 1000)
```

это может уменьшить количество расширений slice и связанных с ними аллокаций.

### `sync.Pool`

Для часто создаваемых временных объектов можно рассмотреть:

```go
pool := sync.Pool{
    New: func() any {
        return new(Buffer)
    },
}
```

Но `sync.Pool` не является универсальным способом ускорить программу: его применение имеет смысл только после измерений и понимания характера нагрузки.

### Структуры вместо лишних указателей

В некоторых структурах данных использование значений вместо большого количества указателей может уменьшить количество объектов, которые GC должен отслеживать.

### Профилирование вместо догадок

Главный принцип:

```text
Сначала измерить
      ↓
Найти bottleneck
      ↓
Изменить код
      ↓
Снова измерить
```

Оптимизация без измерений легко приводит к усложнению кода без реального выигрыша.

# Главная идея

Этот репозиторий — не попытка переписать документацию Go.

Его задача — помочь ответить на вопросы уровня:

> **«Что на самом деле происходит внутри Go, когда я пишу этот код?»**

Понимание runtime, компилятора, памяти и scheduler позволяет лучше интерпретировать профилирование, находить причины проблем с производительностью и осознаннее использовать возможности языка.

```text
Go code
   ↓
Compiler
   ↓
Machine code
   ↓
Runtime
   ↓
Scheduler / Memory / GC
   ↓
OS
   ↓
CPU
```

Чем лучше понятна эта цепочка, тем проще объяснить поведение программы не предположениями, а механизмами, которые действительно происходят внутри Go.
